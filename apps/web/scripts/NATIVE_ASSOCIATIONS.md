# QRguitar native HTTPS association preparation

The app identifier stays `com.qrguitar.app`. Expo config declares iOS Associated Domains for `qrguitar.com` and `www.qrguitar.com`, and separate Android HTTPS/autoVerify intent filters restricted to `/i/` on those hosts. Account, login, privacy-request, admin and service-work pages remain browser routes. The existing native QR parser remains responsible for validating the instrument identity; an OS association never grants access to a private Profile.

## Server integration contract

`lib/native-association.ts` has no environment, Auth, database, network or filesystem dependencies:

- `buildAppleAppSiteAssociation(teamId)` returns the AASA object or `null`.
- `buildAndroidAssetLinks(fingerprints)` returns the Digital Asset Links array or `null`.

The two public App Router handlers read `QRGUITAR_APPLE_TEAM_ID` and `QRGUITAR_ANDROID_SHA256_CERT_FINGERPRINTS` on each request. A missing or syntactically invalid value returns a no-store JSON 404 without reflecting configuration. A valid value returns the association as `application/json`, also no-store; there are no route redirects, authentication checks or database dependencies. One platform can be configured independently. Team IDs require exactly ten uppercase letters/digits. Android accepts one to sixteen explicit colon-delimited SHA-256 certificate fingerprints, supplied as an array or comma-separated value; mixed invalid input disables the whole result. Lowercase hex normalizes to uppercase and duplicate fingerprints collapse.

No values in the tests are production identities. Syntactic validation cannot prove ownership of a Team ID or signing certificate. Do not copy test identities or examples into deployment configuration.

Serve configured files as `application/json` at `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`, directly over HTTPS on each host. Both platforms require direct responses rather than a hostname redirect. The current apex-to-www platform redirect means apex activation remains pending a targeted routing adjustment; adding an app entitlement alone does not verify that host. Signer metadata is public; the association authority is the HTTPS domain and the installed application's configured domains. Preview serving does not prove a production association. [Apple hosting requirements](https://developer.apple.com/library/archive/documentation/General/Conceptual/AppSearch/UniversalLinks.html), [Android website association requirements](https://developer.android.com/training/app-links/configure-assetlinks).

Apple's current `appIDs/components` format restricts the payload to `/i/*`. Do not add web credentials, Handoff, auth callback or all-site scope incidentally. For this new, unpublished app, the expected signed `application-identifier` is `TeamID.com.qrguitar.app`. Legacy or transferred applications can have an App ID prefix different from their Team ID: compare the built entitlement before configuring production, and stop if it differs instead of inventing a prefix. [Expo's current AASA and entitlement configuration](https://docs.expo.dev/linking/ios-universal-links/), [Apple's application-identifier explanation](https://developer.apple.com/library/archive/documentation/General/Conceptual/AppSearch/UniversalLinks.html).

Android's fixed relation grants URL handling for the associated app, while native intent filters enforce the `/i/` path scope on older devices. Android 15+ additionally receives `/i/*` dynamic rules followed by an explicit exclude-all rule. These rules do not broaden the manifest. Keep both real release-signing fingerprints during a deliberate signing rotation when both app generations must work. With Play App Signing, use the **app signing certificate** published in Play Console; an upload-key fingerprint generally does not identify the installed app. Do not include developer debug certificates in production metadata. [Android dynamic rules and signing fingerprints](https://developer.android.com/training/app-links/configure-assetlinks), [Expo Android App Links](https://docs.expo.dev/linking/android-app-links/).

## Evidence and outstanding acceptance

Run `npm --workspace apps/web run test:native-associations` and `node apps/mobile/scripts/check-native-config.mjs` from the repository root. The former tests actual builder output and route handlers, invalid identities, rotation, strict TypeScript and path scope against app config and the actual native parser. The latter runs Expo config introspection and checks the resulting iOS entitlement and Android manifest intent filters. Neither is a signed build or installed-device verification.

Actual Apple/Google developer identities, direct responses on both production domains, a correctly signed installed app, and cold/warm launch tests on devices remain required. On iOS test by tapping a link from another app, because same-domain Safari navigation may intentionally stay in Safari. On Android inspect the OS domain verification state and test both hosts on supported versions; Android 11 and older can fail verification if either host is unavailable. Do not label links verified merely because tests or Expo config pass. [Apple link behavior](https://developer.apple.com/library/archive/documentation/General/Conceptual/AppSearch/UniversalLinks.html), [Android verification](https://developer.android.com/training/app-links/verify-applinks).
