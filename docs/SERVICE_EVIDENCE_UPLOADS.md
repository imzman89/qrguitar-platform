# Private service evidence uploads

Service evidence accepts JPEG, PNG, WebP and PDF files from 1 byte through 15 MiB. File bytes now go directly to Supabase Storage, avoiding the hosting function request-body limit. The app endpoint accepts only JSON instructions up to 16 KiB. Old multipart clients must reload the service editor.

The browser creates one UUID for each chosen upload and prepares its actor/submission/metadata binding against the last confirmed server revision. File bytes go to the exact private signed destination without app credentials. The uninterrupted upload action then explicitly completes that same identity. Completion executes a locked database transaction that verifies Storage object size and MIME metadata and records evidence, activity and its completed receipt together. No byte-signature or malware inspection is claimed.

The four prepare, commit, discard and discovery RPCs are service-role-only. Providers can create evidence for their own draft or changes-requested submission. The existing trusted administrator override remains. Each actor can discover only their own unfinished attempts, including when account restrictions disable mutations. Completed receipts can replay after a submission closes, subject to current account and actor permission checks. A delete creates a receipt tombstone in the existing evidence transaction so delayed completion cannot recreate the deleted attachment. Direct table access remains denied, including service-role access to the three protocol tables.

Protocol v2 uses small action-specific JSON bodies and canonical decimal-string revisions, preserving all PostgreSQL bigint values. Prepare includes immutable file metadata and a nonnull `expectedRevision`; complete and discard include only the original identity and revision. The control response binds `uploadId`, `submissionId`, `actorId`, original `expectedRevision` and current `revision`. Prepare returns `upload` (signed URL), `uploaded` (matching bytes already present), or `committed` (original safe evidence result). An accepted fresh preparation advances its actor/submission scope revision. Competing stale preparations cannot both succeed even if one finishes before the other arrives. UUID identity is also serialized across submissions and the receipt/discard tables.

Mount, Auth changes, **Check upload status**, and **Reload saved version** perform reads only. Accepted unfinished attempts are recovered from the server after a full page reload or a return on another device. Matching bytes offer **Finish existing upload**; missing or mismatched bytes offer explicit discard before a newly chosen file. Discard never attaches or deletes file bytes, and it cannot delete an attachment if completion won the race. It can durably cancel an unknown prepare before that request arrives. Legacy multiple pending attempts remain visible and are resolved one at a time; they are never silently discarded.

The current controller retains an unknown dispatched UUID and original revision until a terminal receipt is confirmed. An empty exact lookup does not prove that a delayed request cannot arrive. A fresh controller requires confirmed server discovery and the attached evidence list before allowing another explicit upload. The server revision fence arbitrates any delayed original prepare. No filenames, File objects, tokens, or upload journal are stored in browser storage. Account transitions clear rendered private state and in-memory file bytes. A file with the same name/size is never assumed to contain the original bytes.

Private reads and deletion keep their existing participant permissions and short-lived preview links. A failed upload completion never deletes a potentially committed object. Abandoned prepared receipts and uncommitted private objects have no automatic retention cleanup in this release. Deletion can report physical cleanup pending after its metadata transaction succeeds. Any future cleanup must coordinate with upload receipts and active signed capabilities.

Apply `20260917210000_service_evidence_uploads.sql` and `20260917211000_release_readiness.sql` after the historical `.4` migrations, followed by `20260917220000_service_evidence_recovery.sql`, `20260917220500_site_editor_helper_permissions.sql` and `20260917221000_release_readiness.sql`. The helper-permission migration explicitly removes Supabase's default API execution grants from two internal site-editor helpers; trigger and editor API behavior remain unchanged. Promote only when the `.6` readiness contract passes all 14 checks. It covers exact functions, receipt columns, constraints, indexes, triggers, permissions and the private bucket's size/MIME settings. Existing v1 rows retain null original revisions and can be explicitly finished or discarded. Old v1 mutation RPCs become finite HTTP426 upgrade stubs; old browser JSON receives full-page refresh guidance and performs no mutation. No customer files or history are cleaned up by these migrations.
